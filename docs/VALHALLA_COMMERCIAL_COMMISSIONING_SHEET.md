2. Verify the Ohio PostgreSQL identity using the dashboard. Use an empty `valhalla_staging`, an empty external database allowlist and new staging-owned secrets. If initial creation triggers a build before assigned values are available, treat it as unaccepted and keep traffic and credentials blocked until guarded preflight succeeds. Restore the standard start command after a successful migration and verify the revision. Hold the Free route if startup time, memory or migrations cannot be verified. Record the pinned build, private database identity, migration head and HTTP 200 readiness.
3. Set `VALHALLA_PREVIEW_ORIGIN` and `CORS_ALLOWED_ORIGINS` to the same exact observed Preview origin. Run the [credential-free curl commands](CODEX_RESUME_2026-12-01.md#operator-sequence-and-record-of-evidence) with one distinct controlled negative origin. Require trusted TLS, no redirect, `/readyz` HTTP 200, and `OPTIONS /api/weweb/login` HTTP 200 with exactly one matching `Access-Control-Allow-Origin` and authorization/content-type headers for POST. The canonical middleware returns HTTP 400 and no allow-origin for the negative request. Record UTC, request origin, status and CORS response headers only. Next run the same check in the actual Preview and use distinct disposable owner, buyer and foreign-scope sessions. Capture tenant denials, logout and replay denial. Keep bearer tokens, cookie values and network exports with secrets out of receipts.
