### Disposable local browser acceptance

The connected workspace still exposes the two existing Free projects and no isolated project. The provider restricts the connector's project creation by account. The recorded refusal does not identify a quota or require a paid plan. The owner can verify whether **New Project** in the signed-in dashboard allows an empty **Valhalla Staging Preview** at $0. If the dashboard also blocks creation, record its exact message and check account eligibility with WeWeb. The primary and backup are excluded from this test. Published staging remains a separate paid option.

Run from an isolated checkout with the existing backend test dependencies, Node and Playwright Chromium. The hosted PR workflow installs its disposable browser and writes the evidence artifact. To run the same check locally on Linux:

```bash
npm install --prefix /tmp/valhalla-browser --ignore-scripts playwright@1.55.1
/tmp/valhalla-browser/node_modules/.bin/playwright install chromium --only-shell
NODE_PATH=/tmp/valhalla-browser/node_modules python scripts/local_browser_acceptance.py --report /tmp/valhalla-browser-evidence.json
```

The test binds a temporary API and fixture client to loopback, uses the canonical authentication and owner routes, and starts separate browser contexts for owner and buyer. It reads the persisted emergency stop and verifies the browser session cannot change operator state. After the scoped fixture recovers, it reads the exact Loki result and Mimir outcomes after the disk database connection is reopened. It exercises the guided startup flow, including an invalid checkpoint, resumption in a new session and revoked bearer replay. The separate Loki receipt regression checks independent reviewer authentication over HTTP. The test runner shuts down its listener and browser and uses no real provider credentials. Rehearsal fixture effects do not authorize real operations.

The report labels this **local browser acceptance**. It does not exercise WeWeb runtime bindings, cross-origin CORS, hosted persistence, 24-hour operation, WeWeb device/browser differences or native Stripe. Keep WeWeb-specific acceptance open until the separate unpublished project has an approved HTTPS API binding and real Preview origin, then repeat with fresh disposable owner and buyer accounts. Production, published staging, expenses and Stripe sandbox activation remain outside this authorization.

## Exact proposed configuration

Create **Valhalla Isolated Staging**, a separate Render Hobby workspace, in **Ohio** for all staging compute and databases. Render allows up to five Hobby workspaces subject to account limits. A different workspace and region provide separate Render private networks. Do not share environment groups, repositories with broader write scope, recovery endpoints, webhook endpoints, external database allowlists or credentials with the existing workspace. Link the repository with the minimum available deployment access. Use the checked-in Dockerfile and repository root for build context. Disable automatic deploys and verify the actual deployment SHA before continuing. Use dashboard manual **Deploy a specific commit**. The root `render.yaml` defines production resources and must not be applied to staging. ### Environment and identity bindings

- **All three services** use `APP_ENV=staging`, `ENV=staging` and `VALHALLA_STAGING_API_ORIGIN` equal to the assigned and approved HTTPS origin. Leave production integrations, outbound email, live writes and startup password reset off. Use an environment without inherited credentials. Check SHA on every service before acceptance.
- **API and operating worker** set `VALHALLA_STAGING_DATABASE_HOST` to the exact new Render internal hostname and `DATABASE_URL` to its internal PostgreSQL connection for `valhalla_staging`. The worker uses its own disposable `VALHALLA_JWT_SECRET` solely for application initialization. It does not share the API signer or receive external operator credentials.
- **API only** sets `VALHALLA_PREVIEW_ORIGIN` and `CORS_ALLOWED_ORIGINS` to the same single browser origin, including port if nondefault. Set the preview project's `API_BASE_URL` and `OWNER_ATTENTION_PREVIEW_ORIGIN` to the approved API origin and `CURRENT_ENV=staging`. Keep `VALHALLA_OWNER_EMAIL`, stage JWT signer, distinct Factory, Prime and owner mandate keys, and the API side of the reviewer identity binding in private configuration. WeWeb gets no server keys.
- **Operating worker, after approval** uses `VALHALLA_STAGING_TRIAL_ENABLED=1`, `VALHALLA_STAGING_PANTHEON_ROLE=MIMIR`, `VALHALLA_FOUNDRY_DISCOVERY_WORKER_ENABLED=1`, `VALHALLA_PANTHEON_WORKER_ENABLED=1`, `VALHALLA_SPECIALIST_WORKER_ENABLED=1` and `VALHALLA_INTERNAL_FACTORY_WORKER_ENABLED=1`. **Loki, after approval** uses `VALHALLA_STAGING_TRIAL_ENABLED=1`, `VALHALLA_LOKI_ANALYST_ENABLED=1`, `VALHALLA_LOKI_QUEUE_URL` equal to the staging API and the matching `VALHALLA_LOKI_REVIEWER_ID` and independent `VALHALLA_LOKI_REVIEWER_KEY`. Start both services with the trial flag absent.
- **Stripe on API only** sets `VALHALLA_STRIPE_EVENT_MODE=test`, sandbox `VALHALLA_STRIPE_ACCOUNT_ID`, `VALHALLA_STRIPE_TEST_WEBHOOK_SECRET` and `VALHALLA_STRIPE_READBACK_KEY` when approved. Start with `VALHALLA_STRIPE_READBACK_ENABLED=0`. Enable restricted readback for the acceptance window alone. Leave `VALHALLA_STRIPE_DELIVERY_ENABLED`, `VALHALLA_STRIPE_BANK_BOOKING_ENABLED` and recurring worker off. Use sandbox callback at `<approved API origin>/webhooks/stripe` for `payment_intent.succeeded` and `charge.refunded`. Require signed sandbox data with `livemode=false`.
- **Application users** are `staging-owner@example.invalid`, `staging-buyer@example.invalid` and `staging-denied@example.invalid` as proposed synthetic logins, each with its own disposable password. Use the pinned migration models `UserProfile` and `AccountSettings` and the same password hasher used in `test_product_artifact_workflow.py` from a guarded staging operator shell. Store passwords safely and never print them. Only the owner matches `VALHALLA_OWNER_EMAIL`. Bind the buyer to the approved fixture tenant and order. Place the third subject in a distinct fixture tenant with no permissions on the approved fixture. Create only `legacy-north / workshop / micro_saas / CA-MB` work, associated synthetic scopes and the one CAD $25.00 test listing and artifact from the authorization sheet.

## Commissioning sequence

1. **Provisioning decision.** Approve the new workspace, region, exact plans, short-lived restore and proposed USD $5 ceiling. Confirm Hobby quota, access to an approved WeWeb editor project, Render memory/price estimates, dedicated sandbox access and private credential custody. No creator action before this approval.
2. **Create the isolated environment.** Provision empty PostgreSQL and staging services. Set auto-deploy Off and leave both worker trial flags absent. Record actual resource IDs, database private host and assigned HTTPS API origin. Provision a distinct WeWeb project and wire only its approved staging bindings. Open the isolated editor Preview with data loading disabled. Inspect the application frame origin in browser developer tools before supplying a token. Configure CORS, then verify the observed origin on a credential-free preflight. An editor hostname alone does not establish the application origin. If the separate project cannot support real session isolation, hold instead of publishing the existing app.
3. **Verify build and recovery inputs.** Deploy the exact reviewed SHA to the API, using the preflight and migration command, then record `/readyz`, deployment SHA, migration head and database identity from the staging operator shell. Keep the DB external allowlist empty. Record the clean snapshot or a paid PITR recovery timestamp. Startup preflight checks only configuration, so compare account identities, secret separation and resource assignments in the dashboard.
4. **Seed and check synthetic access.** In the staging shell run `python /app/scripts/staging_preflight.py api` first, then create the three disposable users and one fixture as documented above. Verify scoped owner and buyer sessions, denied cross-scope actions, logout/reconnect, positive exact-origin CORS and a denied origin. Confirm the emergency stop and persisted live hold. Keep stdout and browser logs redacted. Establish the signed sandbox callback and exact test key scope without processing a payment before trial approval.
5. **Trial decision.** Fill the authorization sheet with exact resource IDs, origins, source snapshot and separately approved restore label, operator and backup, reviewer custodian, and confirmed 24-hour UTC window. Sign the exact SHA and sandbox permissions. Then release the staging-only worker hold and time-limited readback. Verify one received and persisted review in each Loki lane, scope denial, exact-once replay, interruption and recovery. Verify checkout, signature, readback, full refund and that product bytes, acknowledgment, released cash and ledger postings stay blocked. An unmatched or unavailable provider receipt stays open.
6. **Restore and close.** Use the priced, approved temporary restore instance and verify it independently. Compare migration head and a bounded fixture digest/receipt. The restorer must never point the API, operating worker or reviewer at the restore target during the proof. Collect full UTC evidence and stop on unexpected live signals, scope mismatch, repeated effects, failed stop, or irreconcilable receipts. At close, disable the worker trial flags and sandbox listener/readback, revoke test credentials, and record retention. Have the owner approve any later deletion; a running paid resource continues to accrue charges.
